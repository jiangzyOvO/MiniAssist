## 我们究竟要解决什么？

用户往往描述的是现象，而不是一个条件完整的技术问题。

例如：

> 我有一台 Mini 4 Pro，想用以前的遥控器连接，为什么连不上？

系统需要知道遥控器的完整信号，再查兼容说明；必要时还需要结合固件记录和对频步骤。相关信息分散在不同资料中，结论也可能受到设备组合和版本限制。

MiniAssist 是基于 LangGraph 和 Elasticsearch 混合检索的中文产品技术支持 RAG 原型。V1 以 DJI Mini 4 Pro 官方资料为主体，覆盖相关遥控器、配件和版本条件，支持多轮澄清、有限补检索及带来源的回答。项目自建 150 道审核问答，分别评估检索证据覆盖、答案质量和运行稳定性。

## 数据集：知识语料与评测问答

项目中有两份用途不同的数据。

|数据|内容|用途|
|---|---|---|
|知识语料|官方用户手册、固件发布记录、兼容说明、FAQ 等|解析、切分后供系统检索|
|评测问答|根据资料制作的问题、参考答案和证据标注|检查检索是否找到必要依据，以及后续回答是否正确|

## 证据标注

以Q012为例：

> 刚落地、没有关机、电池还很热，充不进去就是充电器坏了吗？

回答至少需要两组必要证据：

|证据组|要证明的事实|
|---|---|
|E1|飞行器开机时不支持机身充电|
|E2|飞行后需要恢复到允许的充电温度，允许范围为 5℃至 40℃|

每组证据保存官方原文范围、来源、页码，并在必要时附上设备或章节等上下文定位。
如果同一事实存在多个有效官方出处，可以设置可替代的证据路径：完整找到其中一条即可。

## 解析(parsing)

解析是把PDF、网页转换成程序能够处理的结构数据。
示例：

```json
{
  "类型": "表格",
  "来源": "飞行眼镜 3 适配说明",
  "页码": 2,
  "行": [
    {
      "遥控器": "RC-N2",
      "飞行器": "Air 3",
      "固件要求": "v01.00.0700 及以上"
    },
    {
      "遥控器": "RC-N2",
      "飞行器": "Mini 4 Pro",
      "固件要求": "v01.01.0300 及以上"
    }
  ]
}
```

| 工作        | 做法                        | 目的                 |
| --------- | ------------------------- | ------------------ |
| 恢复章节与阅读顺序 | 利用书签、字号、位置识别章节，处理双栏与跨页延续  | 避免正文交错或步骤归属错误      |
| 恢复表格关系    | 根据表格线、单元格位置和部分表格的底色边界恢复行列 | 保留型号、条件和数值的对应关系    |
| 关联上下文     | 保存章节路径、设备分类和脚注依赖          | 避免参数脱离适用条件         |
| 解析网页      | 提取 FAQ、技术参数、折叠答案和脚注       | 避免只提取问题、漏掉答案       |
| 建立原文映射    | 将输出文字对应回固定版本的逐页提取文本       | 让后续切分结果可以按真实原文范围评测 |

## 切分(Chunking)

“为什么我这么切分？“
比起“因为这样比较好”，更多的是要突出自己的针对性和优势

- 针对性在于，针对资料中的兼容表、操作条件和固件记录，设计保留相关结构关系的切分规则，并与固定长度、普通递归进行对照
- 优势，横向对比，跑检索看召回率

三种方法，固定长度、递归、结构感知

11道开发集上，

| 切分方式 | BM25 Recall@5 | 向量 Recall@5 | 混合 Recall@5 |
| ---- | ------------- | ----------- | ----------- |
| 固定长度 | 77.3%         | 63.6%       | 81.8%       |
| 递归   | **86.4%**     | 63.6%       | 72.7%       |
| 结构感知 | 72.7%         | 54.5%       | 77.3%       |

- 把同一次固件发布的信息尽量放在一起。

## LangGraph问答流程

设计LangGraph内部架构，支持证据判断、追问、有限补检索和引用校验

```text
理解问题，保留用户原话，整理型号、症状、版本等信息
  → 首轮混合检索 Top-5
  → 关联上下文扩展：最多补 2 块同次固件发布的信息
  → 判断各项需求的证据是否充分，并选择证据
      ├─ 足够 → 生成
      ├─ 缺少可检索的依据 → 补查，再次判断和选择证据
      │                    最多一轮、两条子查询，每条 Top-5
      ├─ 缺少用户必须提供的信息 → 追问
      └─ 无法补足 → 部分回答或说明资料不足
  → 生成答案与引用
  → 引用及信息归属校验，失败最多修复一次
  → answered / partial / insufficient / clarify / error
```

## 开发阶段验证：补检索是否有效，以及为什么有效

选定“结构感知切分+9:1加权混合检索”为基座后，我们实现了问题理解、首轮检索、关联上下文扩展、证据判断、有限补检索、生成与引用校验。

接下来重点验证三个问题：

1. 补检索是否提高必要证据覆盖和答案完整正确率？
2. 收益来自于针对性补查，还是仅仅因为给模型看了更多内容？
3. 找到证据以后，模型能否正确选择并完整使用？

本阶段使用开发集选出的18题，其中12道事实题包含20个必须证据组。

### 1. 模型存在漏判证据缺口

12道事实题的最终上下文覆盖了18/20个必须证据组，10/12题完整覆盖。
剩余问题：

|案例|系统漏了什么|为什么加入规则|
|---|---|---|
|Q001：短按电源键却没开机|找到了开机步骤，但没有核对“单独短按到底有什么作用”|遇到“执行某动作却没达到目标”，分别查**动作本身的作用**和**达到目标的完整步骤**|
|Q046：涉及明确版本的手册与发布记录对照|没找到手册封面的版本、年月证据|用户明确提到手册版本时，增加一次**文档版本依据核对**|

这些原文已经存在于知识库中，但没有进入首轮Top-5；判断节点也没有充分识别缺口。
我们先强化提示词，实际试跑仍有遗漏，随后加入窄范围句式规则，后续回归达到 20/20 个必须证据组覆盖

### 2. A/B对照：整套补检索策略有没有实际收益？

单独展示修复后的成功案例，不足以说明补检索的价值。因此，在相同初始输入下，对比启用和禁用补检索的效果。
两组共享问题、理解结果、首轮Top-5、关联上下文、模型配置和生成校验

|组别|设置|含义|
|---|---|---|
|A|`max_retrieval_rounds=0` ＋ `NoExtraRetrieval`|仅使用初始上下文|
|B|`max_retrieval_rounds=1` ＋ `surface_verification=True`|允许模型补查，并启用句式规则|

结果如下：

|指标|A|B|
|---|---|---|
|共享初始上下文覆盖|14/20|14/20|
|最终必需组覆盖|14/20|**19/20**|
|完整覆盖事实题|6/12|**11/12**|
|额外查询数|0|9|
|未带回新必需证据的查询|不适用|2/9|
|初始上下文之后的平均耗时|5.21 秒|6.43 秒|
|执行报错|0 题|1 题|

人工审核结果：

|指标|A|B|
|---|---|---|
|正确|12|16|
|部分正确|5|0|
|错误|1|1|
|技术失败|0|1|

结论：B找到了更多必要证据，人工审核的完整正确答案也更多，但增加了查询和处理成本。

### 5. 删除与Oracle：补回的证据是否真正影响答案？

证据覆盖与答案质量一起提高，还不足以说明某几块证据发挥了什么作用。因此，对五个历史赢点做直接的上下文干预。

|实验|操作|要检查的问题|
|---|---|---|
|B 重跑 → 删除关键证据|删除补回目标缺口的证据块，重新生成|拿走这些证据后，答案是否退步？|
|A 重跑 → 加入 Oracle 证据|按金标补入覆盖目标缺口所需的最少完整文档块，再判断、生成|直接提供所需证据后，模型能否用好？|

Oracle 只补官方原文，不向模型提供参考答案

|五题配对实验|对照完整正确|干预后完整正确|
|---|---|---|
|B 重跑 → 删除关键证据|4/5|0/5|
|A 重跑 → 补入 Oracle 证据|0/5|4/5|

### 6. C的设计：从“检查证据够不够“到“逐项检查问题是否被回答“

前面的实验支持针对性补检索的价值，但也暴露出另一个问题：**找到必要证据，不代表模型会完整使用它。**
例如：

- Q001 在 Oracle 实验中已经补齐并选中了必要证据，最终答案仍遗漏“单独短按显示电量”。
- Q046 在 B 重跑时已经选中相关封面证据，答案仍出现遗漏。

因此，继续增加检索次数未必能解决问题。我们需要分别检查：

1. 用户的问题包含哪些必须回答的要点？
2. 每个要点有没有足够证据？
3. 最终答案是否覆盖这些要点，写出的结论是否有依据？

基于这一动机，设计候选策略 C：

```text
仅根据用户原话，拆出必须回答的要点
  → 逐项判断现有证据是否支持
  → 针对缺失或冲突的必需要点补查
  → 根据要点清单和所选证据生成答案
  → 检查是否漏答、是否存在无依据结论
  → 最多修订一次，再次检查
```

这里的“要点”即 aspect。例如，“为什么短按没开机”可以拆成：

- 单独短按的作用是什么？
- 正确开机需要什么操作？

### 7. 对比发现：C 的额外检查没有带来预期收益

## RAGChecker联合评估

选定方案后，不再根据测试结果调整本轮策略。使用同一冻结版本，对 60 道测试题各执行三次，保留全部 180 份结果，检查模型输出的波动。
评估分为三层：

|评估方式|检查什么|
|---|---|
|必需证据组覆盖|是否检索到、选中了人工标注的必要依据|
|答案级人工审核|是否回答完整、正确，是否存在技术失败|
|RAGChecker|从抽取的事实陈述出发，分析回答与参考答案、检索上下文之间的关系|

结果如下：

|指标|第一次|第二次|第三次|
|---|---|---|---|
|人工完整正确率|95.00%|91.67%|95.00%|
|技术失败|2|4|3|
|RAGChecker F1|66.14%|63.17%|67.89%|
|RAGChecker faithfulness|91.74%|90.72%|92.57%|

三次运行共 169 份正确、2 份部分正确、9 份技术失败，完整正确率为 169/180＝93.89%，技术失败率为 5%。180 份结果来自 60 道题的重复执行，不是 180 道独立问题。

RAGChecker 仅对 171 份成功交付答案评分，其 F1 三轮均值为 65.73%，faithfulness 均值为 91.68%。
